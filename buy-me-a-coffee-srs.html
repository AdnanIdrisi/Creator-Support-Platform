Buy Me a Coffee

A backend for creators to accept small payments from their supporters. Creators get a public page, supporters buy them coffees through Razorpay, and creators see where the money came from on a dashboard.

4 days × 1.5 hrs Node + Express MongoDB + Mongoose Redis Razorpay (test mode)
01
Overview
What we are building, who uses it, and which topics it makes you practice

A creator signs up and gets a public page at /u/:username. Anyone visiting that page can buy the creator 1 to 5 coffees, pay through Razorpay, and leave a short message. The creator logs in to a dashboard that shows total earnings, earnings per day, and their biggest supporters.

This is a backend-centric project. The only frontend is one static test page served by Express that opens Razorpay Checkout, because the payment signature can only come from a real checkout. Everything else is tested with Postman.

Actors

ActorHas an account?What they do
CreatorYesRegisters, logs in, edits their profile and coffee price, and views the dashboard.
SupporterNo, pays as a guestOpens a creator page, enters name, email and message, and pays for coffees.
RazorpayExternal systemCreates orders, collects the payment, and returns a signature the backend must verify.

Topics this project practices

TopicWhere it shows up in the project
Access + refresh tokensCreator login with a 15-minute access token, a 7-day refresh token in an httpOnly cookie, rotation on every refresh, and logout that revokes the session.
Payment gatewayRazorpay order creation with a server-computed amount, then HMAC signature verification before a payment is counted.
Aggregation pipelineDashboard summary, earnings per day (IST), top supporters, and the public page stats.
IndexingUnique indexes, a compound index for dashboard queries, a TTL index that auto-deletes expired refresh tokens, and an explain() before/after comparison.
CachingRedis cache-aside for the public page and leaderboard, with invalidation when a payment is verified or a profile changes.

Already covered before this project and assumed known: REST APIs, basic authentication, Mongoose models, Express middleware, frontend–backend integration and the Vite proxy. This SRS does not re-teach them.

Entities & indexes
Three collections, and the indexes each query depends on

User (creator)

FieldTypeRules
nameStringRequired, 2–50 chars.
usernameStringRequired, unique, lowercase, 3–30 chars, only a-z 0-9 _. Used in the public URL.
emailStringRequired, unique, lowercase.
passwordStringbcrypt hash. select: false so it is never returned by default.
bioStringOptional, max 160 chars.
avatarUrlStringOptional plain URL. No file upload.
coffeePriceNumberPrice of one coffee in rupees. Integer, ₹20–₹500, default ₹50.
createdAt / updatedAtDateMongoose timestamps.

Support (one payment)

FieldTypeRules
creatorIdObjectId → UserRequired. The creator being supported.
supporterNameStringRequired, 2–50 chars. Shown publicly.
supporterEmailStringRequired, lowercase. Used to group supporters. Never shown on public endpoints.
messageStringOptional, max 200 chars.
coffeesNumberInteger, 1–5.
amountNumberTotal in paise (integer). Computed on the server.
currencyStringAlways INR.
statusenumcreated → paid or failed. Default created.
razorpayOrderIdStringRequired, unique.
razorpayPaymentIdStringSet after verification.
paidAtDateSet when status becomes paid.
createdAt / updatedAtDateMongoose timestamps.

RefreshToken (one login session)

FieldTypeRules
userIdObjectId → UserRequired.
tokenHashStringSHA-256 hash of the refresh token. The raw token is never stored.
expiresAtDateNow + 7 days. MongoDB deletes the document automatically after this time.
createdAtDateMongoose timestamp.

Indexes

CollectionIndexWhy it exists
users{ username: 1 } uniqueEvery public page request looks up a creator by username.
users{ email: 1 } uniqueLogin lookup and duplicate-account check.
supports{ creatorId: 1, status: 1, createdAt: -1 }Serves every dashboard and public query: "this creator's paid supports, newest first".
supports{ razorpayOrderId: 1 } uniqueVerify looks up the support by order id. Unique also blocks duplicate orders.
refreshtokens{ tokenHash: 1 } uniqueRefresh and logout look up the session by token hash.
refreshtokens{ expiresAt: 1 } TTL, expireAfterSeconds 0Expired sessions are cleaned up by MongoDB, no cron job needed.
Mongoose · index definitions
supportSchema.index({ creatorId: 1, status: 1, createdAt: -1 });
supportSchema.index({ razorpayOrderId: 1 }, { unique: true });

refreshTokenSchema.index({ tokenHash: 1 }, { unique: true });
refreshTokenSchema.index({ expiresAt: 1 }, { expireAfterSeconds: 0 }); // TTL index
Key concept

A compound index works left to right. { creatorId, status, createdAt } serves a query that filters on creatorId and status and sorts by createdAt, all in one index scan. A query that filters only on status cannot use it, because it skips the first field.

Why is amount stored in paise as an integer instead of rupees with decimals?

A query filters { creatorId, status: "paid" } and sorts by createdAt: -1. Does the compound index cover it?

04
Core flows
The three sequences every student must be able to explain

Payment flow

Supporter picks coffees and submits the form
Test page sends username, name, email, message and coffee count to POST /api/payments/order.
Server computes the amount and creates a Razorpay order
Saves a Support with status created and the returned razorpayOrderId.
Razorpay Checkout opens in the browser
Supporter pays with a test card or UPI. Checkout returns order id, payment id and signature.
Page sends the three values to verify
Server computes HMAC-SHA256 of order_id|payment_id using the key secret and compares it with the signature.
Match → support is marked paid, cache is cleared
Status paid, paymentId and paidAt saved. Page and leaderboard cache keys for that creator are deleted.
⚠️

Never mark a payment paid because the frontend said so. The Checkout success callback runs in the supporter's browser, and anyone can call your verify endpoint with made-up ids. Only a matching signature proves Razorpay processed the payment.

Token refresh flow

Access token expires after 15 minutes
A protected request returns 401.
Client calls POST /api/auth/refresh
The browser attaches the httpOnly refresh cookie automatically.
Server verifies the JWT, hashes it, and looks up the hash
Found → delete that document. Valid JWT but not found → it was already used, so revoke every session of this user and return 401.
New refresh token saved, new access token returned
Each refresh token works exactly once. That is rotation.

Cache-aside flow for the public page

GET /api/creators/ankur
    ↓
Redis GET creator:ankur:page
    ├─ HIT → return cached JSON, header X-Cache: HIT (no MongoDB query)
    └─ MISS → query MongoDB + aggregation → Redis SET with 300s TTL → X-Cache: MISS
    ↓
Payment verified or profile updated → Redis DEL creator:ankur:page (+ :leaderboard)

05
Functional requirements
What the system must do. "Must" items are required, "Should" items are stretch goals.
IDRequirementPriority
Auth & sessions
FR-01A creator can register with name, username, email and password. Duplicate username or email returns 409.Must
FR-02Login returns a 15-minute access token in the body and sets a 7-day refresh token as an httpOnly cookie. The refresh token's hash is saved in RefreshToken.Must
FR-03Protected routes read the access token from Authorization: Bearer. Missing, invalid or expired tokens return 401.Must
FR-04Refresh deletes the old refresh token and issues a new access + refresh pair (rotation).Must
FR-05If a refresh token has a valid signature but is not in the database, all refresh tokens of that user are deleted and 401 is returned (reuse detection).Should
FR-06Logout deletes the current refresh token and clears the cookie.Must
Creator profile & public page
FR-07A creator can update name, bio, avatarUrl and coffeePrice. Username and email cannot be changed.Must
FR-08The public page returns the creator's profile, total coffees, supporter count and the 10 most recent paid supports. Supporter emails are never included.Must
FR-09The public leaderboard returns the top 10 supporters, grouped by supporter email, sorted by total coffees. It shows name and coffees only.Must
FR-10An unknown username returns 404 on every creator and payment endpoint.Must
Payments
FR-11A supporter can buy 1–5 coffees with a name, email and optional message (max 200 chars), without an account.Must
FR-12The server computes amount = coffees × coffeePrice × 100. Any amount sent by the client is ignored.Must
FR-13Creating an order calls Razorpay, saves a Support with status created, and returns orderId, amount, currency and the public keyId.Must
FR-14Verify recomputes the HMAC-SHA256 signature. On match, the support becomes paid with paymentId and paidAt. On mismatch, it becomes failed and the API returns 400.Must
FR-15Verifying an already-paid order returns 200 and changes nothing (idempotent).Must
FR-16Only supports with status paid count anywhere: public page, leaderboard and dashboard.Must
FR-17Express serves one static test page that creates an order, opens Razorpay Checkout and calls verify.Must
Dashboard (aggregation)
FR-18Summary returns total earnings (₹), total coffees, total supports, unique supporters and average coffees per support (1 decimal) from a single pipeline.Must
FR-19Earnings by day covers the last N days (default 30, max 90), grouped by date in Asia/Kolkata, sorted oldest to newest.Must
FR-20Top supporters (default 10, max 50) returns name, email, total coffees, total amount and number of supports.Must
FR-21The supports list is paginated (default 20, max 50), newest first, and returns the total count along with the page.Must
Caching
FR-22The public page and leaderboard use cache-aside in Redis with a 300-second TTL, keys creator:{username}:page and creator:{username}:leaderboard.Must
FR-23A successful verify deletes both cache keys for that creator. A profile update deletes the page key.Must
FR-24Cached endpoints return an X-Cache: HIT or X-Cache: MISS header.Must
FR-25Dashboard endpoints are not cached. The creator must always see fresh numbers after a payment.Must
Indexing
FR-26All indexes in section 02 are defined in the Mongoose schemas.Must
FR-27npm run seed inserts about 50,000 paid supports across 3 creators spread over 90 days.Should
FR-28The supports-list query is run with explain("executionStats") before and after the compound index, and totalDocsExamined plus the plan stage (COLLSCAN vs IXSCAN) are recorded in the README.Should

06
Non-functional requirements
How well the system must do it: security, performance, reliability, code quality
IDCategoryRequirement
NFR-01SecurityPasswords are hashed with bcrypt (cost 10). Password hashes are never returned in any response.
NFR-02SecurityThe refresh cookie is httpOnly, SameSite=Strict, scoped to /api/auth, and Secure in production. Access and refresh tokens use different secrets.
NFR-03SecuritySignature comparison uses crypto.timingSafeEqual. The Razorpay key secret never leaves the server.
NFR-04SecurityAll secrets (JWT secrets, Razorpay keys, Mongo and Redis URLs) come from .env. A .env.example is committed; .env is not.
NFR-05PerformanceA cache hit is served from Redis without any MongoDB query. This is verifiable from the HIT/MISS logs.
NFR-06PerformanceEvery query on supports uses an index (IXSCAN, never COLLSCAN). Pipelines start with a $match on creatorId and status.
NFR-07ReliabilityIf Redis is down, cached endpoints fall back to MongoDB. A cache failure never turns into a 500.
NFR-08ReliabilityA support can only move from created to paid or failed. A paid support never changes again.
NFR-09Data integrityMoney is stored as integer paise and converted to rupees only in responses. Timestamps are stored in UTC and grouped in IST.
NFR-10API qualityEvery request body and query param is validated (express-validator or zod). Errors use one shape: { success: false, message } with the correct status code.
NFR-11MaintainabilityCode is layered into routes, controllers, services and models. Razorpay and Redis clients are created once and reused.
NFR-12ObservabilityThe server logs every cache HIT/MISS and every verify outcome (paid, failed, already paid) with the order id.

Not buildingWhy, and what a real product would do
Supporter accountsSupporters pay as guests. Real products let supporters log in and see their history.
